# Full Project Audit — webfolio-v1-vanilla

**Date:** 2026-06-09
**Scope:** End-to-end review of architecture, code quality, robustness, performance, SEO, accessibility, design/UX, data layer, and Git/repo hygiene.
**Method:** Multi-agent static analysis (JS, HTML/CSS/data, Git) + the Graphify code graph + live visual inspection of all 7 pages in Chrome (rendering, console, network, PT/EN, theme).
**Constraint honored:** The project stays **pure HTML + CSS + vanilla JS — no framework, no npm, no build step.** Every recommendation below is achievable within that constraint. This is the career **v1**; the goal is hardening and de-duplication, **not a rewrite**.

---

This affects findings **M13** and **M14** below and adds a roadmap-render workstream. ## 1. Executive summary

The codebase is **well above "vibe-coded hobby" level**. It uses native ES modules with a single entry point per page, a real design-token system, a clean PT/EN i18n pub/sub pattern, BEM-style CSS, and a disciplined Git workflow (topic branches + PRs, conventional commits, zero AI-coauthorship trailers). The Graphify graph confirms genuine module structure (854 nodes / 929 edges, 100% extracted) with `language.js` (`getCurrentLanguage()`) and the translation keys as central hubs — i.e. i18n is correctly the backbone.

So the honest verdict: **this is not a project that needs to be thrown away.** It needs targeted hardening. The issues cluster into four themes:

1. **Production config is broken in ways a recruiter would see** — three different/wrong canonical domains, and the **resume Experience/Education section does not translate to Portuguese** (confirmed live).
2. **Robustness gaps** — no loading/error states, deploy-fragile relative paths, magic-number `setTimeout` races, and missing null guards.
3. **Duplication** — `loadTranslations()` copy-pasted in 5 modules (causing `translations.json` to be fetched **8× on the homepage**, confirmed in the network panel), a 220-line stale skills fallback, and ~930 lines of duplicated header/footer across pages.
4. **Hygiene** — an inverted `.gitignore` rule, a 778 KB profile image, stale branches, and an unmaintained CHANGELOG.

None are "Critical" in the security sense. Two are **High** because they are visible and undermine the portfolio's core promises (bilingualism, professional polish).

**What works well (keep it):** the no-build ES-module architecture, the token system, the `languageChanged` CustomEvent pattern, GitHub-stats caching, `prefers-reduced-motion` handling, the PR-per-change Git discipline, and the clean dark theme.

## 3. Design & UX critique

Framework: first impression → usability → hierarchy → consistency → accessibility (design-critique skill).

**Overall impression.** Clean, modern, confident dark theme with consistent spacing and a clear type hierarchy. It reads as the work of someone who cares about craft. The biggest opportunities are robustness signals (loading/error states) and finishing the bilingual experience, not visual redesign.

**Usability**

| Finding | Severity | Recommendation |
|---------|----------|----------------|
| Projects "Loading…" button never resolves visibly while GitHub stats enrich | 🟡 Moderate | Resolve to a normal "Refresh" state; show a skeleton on cards, not a stuck button (ties to H5/M3). |
| On a failed fetch the user sees an empty area with no message | 🟡 Moderate | Render an explicit empty/error state ("Couldn't load projects — try again"). (H5) |
| Volunteer cards look clickable but aren't keyboard-operable | 🟡 Moderate | Make them `<button>`s. (M10) |

**Visual hierarchy.** Eye lands correctly on the hero name, then the typewriter subtitle, then the two CTAs — good. On the resume, the **left timeline column is right-aligned**, producing a ragged-right reading edge that's harder to scan than left-aligned body text; consider left-aligning descriptions. The hero subtitle uses a **monospace** font for "Platform Engineer" — distinctive, but confirm it's intentional rather than a fallback.

**Consistency.** Strong: BEM naming, token-driven spacing/colors, repeated card patterns. Minor: 5 hardcoded swatch hexes duplicated in two CSS blocks, and `z-index` literals that bypass the scale.

**Accessibility (WCAG 2.1 AA lens).**

| # | Issue | Criterion | Severity | Recommendation |
|---|-------|-----------|----------|----------------|
| 1 | Yellow theme primary fails contrast | 1.4.3 | 🔴 Critical (in that theme) | Darken action tokens or use dark text on primary. (M12) |
| 2 | No keyboard access to modal-trigger `<div>`s | 2.1.1 | 🟡 Major | Use `<button>`. (M10) |

## 4. Architecture assessment (long-term robustness)

**Module system.** Native ES modules, one `<script type="module">` entry per page, no global namespace pollution. This is the correct build-free pattern and should be **preserved**. The `core / components / pages` split has clean intent.

**The single most valuable refactor** is centralizing translations: make `core/language.js` own a cached, single-fetch translations object and `export` an accessor; have page modules import it and subscribe to `languageChanged`. This one change (a) removes the 5× duplication (M1), (b) eliminates the 8× redundant fetches, and (c) removes the root cause of the `setTimeout` races (M4), because rendering can then await a real "translations ready" signal instead of guessing with timers. It is the keystone of Phase 2 in the plan.

**Duplicated header/footer (~930 lines).** CLAUDE.md declares this intentional (no template engine). The audit confirms the **drift risk is real, not theoretical** — the `footer.tagline` i18n attribute is already missing on 5 of 7 pages (M9). Options, all build-free:

- **A — JS-injected partials** (`fetch('partials/header.html')` into a placeholder): single source of truth, kills drift; cost: header absent until JS runs (FOUC + minor no-JS/SEO hit), must re-run i18n + active-link logic after injection.
- **B — JS template string** (`layout.js` exporting `headerHTML(active)`): no extra fetch, computes the active link automatically; cost: markup lives in JS.
- **C — keep duplication + a drift-guard** (a tiny Node/`grep` consistency check, optionally a pre-commit hook): zero runtime cost, header stays in static HTML (best SEO/perf); cost: doesn't remove duplication, only detects drift.

**Recommendation:** **C now** (cheap, preserves the static-HTML SEO advantage, fixes today's drift), with **A/B documented as a v2 option**. If A/B is adopted later, set the active nav link from `location.pathname` so it stops being hand-edited per page.

**Data fetching.** Centralize, switch to root-relative paths (safe because the site is a user-site at the domain apex), drop `cache:'no-cache'`, add an `AbortController` timeout, and cache the projects-page GitHub enrichment.

## 5. Git & repository hygiene

History is healthy: 116 commits, consistent conventional commits, atomic recent work, **zero AI-coauthorship trailers** (rule respected), and real PR-per-change discipline. `graphify-out/` is correctly git-ignored and never tracked. No secrets, no `node_modules`, no OS junk.

To fix: the inverted `.gitignore` rule (M16), the unmaintained CHANGELOG (M17 — either commit to per-PR `[Unreleased]` bullets or drop the rule; a half-maintained changelog is worse than none), the destructive/over-privileged deploy (M18 — add a "is `index.html` non-empty?" gate, switch to a fine-grained PAT scoped to the prod repo with an expiry), the 778 KB image (M19), and the stale branches (M20 — delete merged branches, enable "auto-delete head branches" on GitHub).

**Recommended branching model (solo, incremental refactor):** lightweight trunk-based / GitHub Flow — `main` always deployable and protected; short-lived `feat|fix|refactor|chore|docs/<slug>` branches, one logical change each; a PR per branch (a deploy gate + diff-review moment even solo); squash- or rebase-merge to keep history linear; tag releases (`v1.0.0`) and cut a dated CHANGELOG section per tag. No `develop` branch — overkill for a solo static site with auto-deploy, and against the project's "radical simplicity" ethos.
